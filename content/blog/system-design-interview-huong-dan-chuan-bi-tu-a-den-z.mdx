# System Design Interview: Hướng Dẫn Chuẩn Bị Từ A-Z

Tôi còn nhớ system design interview đầu tiên của mình tại Google.

Interviewer: *"Thiết kế YouTube."*

45 phút. Whiteboard trống. Tôi và áp lực.

Tôi vẽ vài boxes: "Client, API, Database, Cache..." rồi... im lặng.

Interviewer chờ đợi.

Tôi không biết nói gì tiếp theo.

**Result: Strong No Hire.**

Feedback: *"Candidate has good coding skills but lacks system design thinking and structured approach."*

Đó là lần tôi nhận ra: **System design interview là game hoàn toàn khác với coding interview.**

Sau 2 tháng preparation nghiêm túc và 15+ mock interviews, tôi pass system design rounds tại cả Google và Facebook.

Bài này sẽ chia sẻ mọi thứ tôi học được.

## System Design Interview Là Gì?

### Định Nghĩa

**System design interview test khả năng thiết kế large-scale distributed systems.**

Không phải code. Không phải algorithms. Mà là **architecture thinking**.
```
Coding Interview:
"Implement function để find shortest path"
→ Test: Algorithm knowledge, coding skills

System Design Interview:
"Design Instagram"
→ Test: Architecture thinking, scalability knowledge, 
        trade-off analysis, communication skills
```

### Tại Sao Companies Test System Design?

**Vì đó là work thực tế của Senior Engineers:**
```
Junior Engineer daily work:
- Implement features theo spec
- Fix bugs
- Code reviews
- Follow existing architecture

Senior Engineer daily work:
- Design new systems
- Make architecture decisions
- Evaluate trade-offs
- Lead technical direction
- Review designs

→ System design interview = Simulate Senior Engineer work
```

**Companies muốn biết:**
1. Bạn có think systematically không?
2. Bạn có hiểu distributed systems không?
3. Bạn có make reasonable trade-offs không?
4. Bạn có communicate effectively không?

### System Design Interview Format

**Typical 45-60 phút interview:**
```
0-5 phút: Introduction, icebreaker
5-50 phút: System design problem
50-55 phút: Deep dive vào specific parts
55-60 phút: Questions & wrap up

Core time: 45 phút design
```

**What interviewer observes:**
```
✓ Problem understanding (clarifying questions)
✓ Architecture thinking (high-level design)
✓ Scalability awareness (capacity planning)
✓ Trade-off analysis (justify decisions)
✓ Technical depth (deep dive specific parts)
✓ Communication (think out loud)
```

## Tại Sao System Design Interview Khó?

### Challenge 1: Open-Ended Problem
```
Coding interview:
"Find longest palindrome substring"
→ Clear input, clear output, clear constraints

System design interview:
"Design Twitter"
→ Vague problem, unlimited scope, nhiều cách giải quyết
```

**Bạn phải tự clarify:**
- Scale bao nhiêu? (1K users hay 100M users?)
- Features nào? (Core features hay all features?)
- Constraints gì? (Budget? Timeline? Team?)

### Challenge 2: Không Có "Correct Answer"
```
Coding problem có correct solution.

System design KHÔNG có single correct solution.

Only trade-offs:
- Solution A: Simple, limited scale
- Solution B: Complex, unlimited scale
- Solution C: Balanced, reasonable cost

All are "correct" depending on context!
```

**Interviewer không expect perfect architecture. Expect reasonable trade-offs.**

### Challenge 3: Broad Knowledge Required
```
Coding interview: Deep vào 1 topic (algorithms)

System design interview: Wide knowledge:
- Load balancing
- Caching strategies
- Database scaling
- Message queues
- CDN
- Distributed systems
- Consistency models
- API design
- And more...
```

### Challenge 4: Time Pressure
```
45 phút để:
- Clarify requirements (5 min)
- Estimate scale (5 min)
- Design API (5 min)
- Draw architecture (15 min)
- Deep dive (15 min)

Không đủ time để perfect mọi thứ!
→ Phải prioritize
→ Phải structured
```

## SNAKE Framework: Cách Tiếp Cận Có Cấu Trúc

**Sau khi fail nhiều interviews, tôi học được framework này từ senior architect.**

### S - Scope (5-7 phút)

**Goal: Clarify requirements trước khi design**
```
Questions to ask:

Functional requirements:
"Which features are must-have?
 - Post tweets? ✓
 - Follow users? ✓
 - View timeline? ✓
 - Direct messages? (out of scope)
 - Trending topics? (nice to have)"

Non-functional requirements:
"Scale assumptions:
 - How many users? (100M? 1B?)
 - Daily active users?
 - Tweets per day?
 - Read vs write ratio?
 - Latency requirements? (< 200ms?)
 - Availability? (99.9%? 99.99%?)"

Constraints:
"Any constraints?
 - Existing infrastructure?
 - Budget limits?
 - Timeline?"
```

**Why this matters:**
```
Without clarification:
→ Design cho wrong scale
→ Include unnecessary features
→ Waste time on out-of-scope parts

With clarification:
→ Right-sized solution
→ Focus on what matters
→ Impress interviewer với structured thinking
```

### N - Numbers (5-7 phút)

**Goal: Estimate capacity với back-of-envelope calculations**
```
Example: Twitter

Given (from Scope phase):
- 200M daily active users
- 100M tweets/day
- Read-heavy (95% reads, 5% writes)

Calculate:

Write traffic:
100M tweets/day / 86,400s ≈ 1,200 tweets/second

Read traffic:
200M users × 50 timeline loads/day = 10B loads/day
10B / 86,400s ≈ 115,000 requests/second

Read:Write ratio = 115K : 1.2K ≈ 100:1
→ Read-heavy system
→ Caching CRITICAL

Storage (5 years):
100M tweets/day × 365 × 5 = 182.5B tweets
× 1KB per tweet = 182.5TB
→ Need distributed storage

Bandwidth:
115K req/s × 20 tweets × 1KB = 2.3GB/s
→ CDN essential for media
```

**Why calculations matter:**
```
Numbers inform decisions:
- 100:1 read:write → Optimize for reads (caching)
- 182TB → Need sharding eventually
- 2.3GB/s → Cannot serve without CDN

Without numbers: Guessing
With numbers: Data-driven decisions
```

### A - API (5-7 phút)

**Goal: Define interfaces**
```
Core APIs for Twitter:

POST /v1/tweets
{
  "content": "Hello world!",
  "media_urls": []
}
Response: 201 Created

GET /v1/timeline?cursor={cursor}&limit=20
Response: 200 OK
{
  "tweets": [...],
  "next_cursor": "...",
  "has_more": true
}

POST /v1/tweets/{id}/like
Response: 204 No Content

POST /v1/users/{id}/follow
Response: 204 No Content
```

**Why API first:**
```
API design forces clarity:
- What data client sends?
- What data server returns?
- How to paginate?
- Error handling?

→ Concrete, discussable
→ Shows attention to detail
```

### K - Key Components (15-20 phút)

**Goal: High-level architecture**
```
Draw main components:

[Client] 
   ↓
[Load Balancer]
   ↓
[API Servers] (stateless)
   ↓
[Redis Cache] ← Timeline storage
   ↓
[PostgreSQL] ← Metadata
   ↓
[Kafka Queue] → [Fanout Workers]

Key decisions:

1. Fanout Strategy (CRITICAL for Twitter):
   - Normal users: Fanout on write
   - Celebrities: Fanout on read
   - Why: Avoid celebrity fanout explosion

2. Timeline Cache:
   - Redis sorted sets
   - Store 1000 recent tweets per user
   - Why: Sub-50ms timeline loads

3. Database:
   - PostgreSQL sharded by user_id
   - Why: Strong consistency for critical data
```

**Spend MOST time here. This is the meat.**

### E - Elaborate (10-15 phút)

**Goal: Deep dive vào specific parts**
```
Interviewer might ask:
"Can you elaborate on fanout service?"

Deep dive:

Fanout Implementation:

When user tweets:
1. Save to database
2. Publish to Kafka queue
3. Fanout workers consume
4. For each follower:
   - Insert tweet_id into Redis sorted set
   - Key: timeline:{user_id}
   - Score: timestamp
5. Keep only 1000 recent tweets

Celebrity handling:
- If followers > 10K → Skip fanout
- When follower loads timeline:
  → Merge pre-computed feed + celebrity tweets
  → Sort by timestamp

Trade-offs:
✅ Fast reads (< 50ms from cache)
✅ No celebrity fanout explosion
❌ Slight delay for celebrity tweets (acceptable)
❌ More complexity
```

## Top 5 Câu Hỏi System Design Phổ Biến

### 1. Design Twitter / News Feed

**Core challenge: Fanout to millions of followers**
```
Key topics:
- Fanout strategies (write vs read)
- Timeline generation
- Celebrity problem
- Eventual consistency

Focus areas:
✓ Hybrid fanout (normal vs celebrity users)
✓ Timeline cache design (Redis sorted sets)
✓ Read:Write optimization (95:5 ratio)
✓ Scalability (handle 100M users)

Time allocation:
- Fanout strategy: 40% (most important)
- Cache design: 30%
- Database sharding: 20%
- Other: 10%
```

### 2. Design YouTube / Video Platform

**Core challenge: Encode, store, deliver video globally**
```
Key topics:
- Video upload pipeline
- Encoding (multiple resolutions)
- CDN for delivery
- Storage optimization

Focus areas:
✓ Upload → Encoding → Storage flow
✓ Adaptive bitrate streaming
✓ CDN strategy (cost optimization)
✓ Thumbnail generation

Example numbers:
- 500K uploads/day × 10 min × 1GB = 500TB/day
- Encode to 360p, 720p, 1080p, 4K = 2.5PB/day
- 1B views/day × 5 min = 3 exabytes/month bandwidth
→ CDN critical!
```

### 3. Design WhatsApp / Messaging

**Core challenge: Real-time delivery với high reliability**
```
Key topics:
- WebSocket connections
- Message delivery guarantees
- Offline message handling
- End-to-end encryption (conceptual)

Focus areas:
✓ Real-time delivery (WebSocket)
✓ At-least-once delivery (queue-based)
✓ Delivery receipts (sent, delivered, read)
✓ Group messaging optimization

Architecture highlight:
Client ←→ WebSocket Server → Message Queue → Database
→ Real-time for online users
→ Queue for offline users
```

### 4. Design Google Drive / Dropbox

**Core challenge: Sync files across devices**
```
Key topics:
- Chunking strategy
- Conflict resolution
- Delta sync
- Metadata management

Focus areas:
✓ File chunking (4MB chunks)
✓ Hash comparison (only upload changed chunks)
✓ Conflict detection (version history)
✓ Real-time notifications

Bandwidth savings:
- Without chunking: Re-upload entire 1GB file
- With chunking: Upload only 1 changed chunk (4MB)
→ 250x bandwidth savings!
```

### 5. Design URL Shortener

**Core challenge: Generate unique short URLs**
```
Key topics:
- Short code generation
- Redirect mechanism
- Analytics tracking
- Scale estimation

Focus areas:
✓ Base62 encoding (a-z, A-Z, 0-9)
✓ Collision handling
✓ Database sharding (if needed)
✓ Cache hot URLs

Simple but covers fundamentals:
- Database design
- API design
- Caching strategy
- Scale calculations
```

## Common Mistakes Trong System Design Interview

### Mistake 1: Jump to Solution
```
❌ Bad:
Interviewer: "Design Twitter"
Candidate: "OK, we'll use Kafka, Cassandra, 
           microservices, Kubernetes..."

→ No requirements gathering
→ No calculations
→ Generic architecture

✅ Good:
Interviewer: "Design Twitter"
Candidate: "Let me first clarify:
           - Expected scale?
           - Core features?
           - Read vs write ratio?
           ..."

→ Structured approach
→ Shows thinking process
```

### Mistake 2: No Trade-off Discussion
```
❌ Bad:
"We use cache because it's fast."

→ Surface level
→ No depth

✅ Good:
"We use Redis cache for timelines because:
 ✅ 95% reads → High cache hit rate
 ✅ Sub-10ms latency requirement
 ❌ Trade-off: Stale data possible (mitigated with TTL)
 ❌ Trade-off: $1K/month cost (acceptable for 100M users)
 
 Decision: Benefits outweigh costs."

→ Shows understanding
→ Justifies decisions
```

### Mistake 3: Over-Engineering
```
❌ Bad:
"For 10K users, we'll use Kubernetes, 
 Kafka, Cassandra, microservices..."

→ Overkill
→ Shows poor judgment

✅ Good:
"For 10K users:
 - Monolith on Heroku ($200/month)
 - PostgreSQL ($50/month)
 - Redis for sessions ($50/month)
 
 When reach 100K users, can refactor.
 Right now, ship fast > perfect architecture."

→ Right-sized solution
→ Evolution path clear
```

### Mistake 4: Silent Design
```
❌ Bad:
[Draws diagram silently for 10 minutes]

→ Interviewer doesn't know what you're thinking
→ Cannot provide guidance

✅ Good:
"I'm drawing the architecture.
 Starting with client layer...
 Now adding API servers...
 Here's the cache layer...
 Let me connect them..."

→ Think out loud
→ Engage interviewer
→ Get feedback early
```

### Mistake 5: Ignore Interviewer Hints
```
❌ Bad:
Interviewer: "How do you handle celebrity users?"
Candidate: "Let me finish database design first..."

→ Not listening
→ Missing guidance

✅ Good:
Interviewer: "How do you handle celebrity users?"
Candidate: "Great question. For celebrities with
           > 10K followers, I'd use pull model
           instead of push to avoid fanout explosion..."

→ Responsive
→ Flexible
→ Collaborative
```

## Strategies Để Pass System Design Interview

### Strategy 1: Follow Framework Religiously
```
SNAKE framework (45 phút):
- Scope: 7 phút
- Numbers: 7 phút
- API: 7 phút
- Key components: 15 phút
- Elaborate: 9 phút

Practice với timer!
Discipline = Success
```

### Strategy 2: Think Out Loud
```
Continuous narration:

"I'm considering two approaches:
 Option A: Fanout on write
 Option B: Fanout on read
 
 Given 95% reads, Option A makes sense because...
 
 Let me draw this out...
 
 Here I'm showing the cache layer...
 
 The trade-off here is..."

→ Interviewer follows your thinking
→ Can provide hints
→ Shows communication skills
```

### Strategy 3: Focus on Bottlenecks
```
Always identify THE critical challenge:

Twitter → Fanout problem
YouTube → Video encoding + delivery
WhatsApp → Real-time delivery
Google Drive → File sync

Spend 60% time on bottleneck
40% time on other parts

→ Shows prioritization
→ Demonstrates depth
```

### Strategy 4: Use Numbers
```
Don't say: "We need caching"

Say: "With 115K reads/second and database
      handling max 10K reads/second, we need
      caching to reduce DB load by 90%.
      Redis can handle 100K reads/second,
      which gives us headroom."

→ Data-driven decisions
→ Shows scale awareness
```

### Strategy 5: Acknowledge Limitations
```
Good architect knows limitations:

"This design handles 1M users well.
 At 10M users, we'd need to:
 - Shard database
 - Add CDN for media
 - Geographic distribution
 
 But for current scope, this is appropriate."

→ Shows growth thinking
→ Demonstrates judgment
→ Not over-engineering
```

## Key Takeaways

**System design interview tests:**
```
✓ Architecture thinking (not coding)
✓ Scalability awareness (handle millions)
✓ Trade-off analysis (justify decisions)
✓ Communication (think out loud)
✓ Technical depth (know your components)
```

**Success formula:**
```
SNAKE Framework + Practice + Feedback = Pass

Framework: Structured approach
Practice: Build muscle memory
Feedback: Improve continuously
```

**Common mistakes to avoid:**
```
✗ Jump to solution (clarify first!)
✗ No trade-offs (always discuss)
✗ Over-engineering (right-size solution)
✗ Silent design (think out loud)
✗ Ignore hints (be flexible)
```

**Preparation roadmap:**
```
Foundation (4-6 weeks):
- Mental models
- Core components
- Distributed systems basics

Practice (4-6 weeks):
- Simple → Medium → Complex
- Time management
- Framework mastery

Mock interviews (2-4 weeks):
- Peer practice
- Professional mocks
- Iterate based on feedback

Total: 10-16 weeks of consistent practice
```

**Remember:**
```
System design interview không test knowledge
Mà test thinking process

Perfect architecture không tồn tại
Only appropriate architecture cho context

Communication skills = Technical skills
Both are evaluated

Practice consistently
Get feedback
Improve continuously

You can do this!
```
